# Board profiles

Adapt profiles to hardware that has actually been inspected. A board name or
USB-UART bridge alone is insufficient to establish chip, flash or PSRAM.
The ESP32 prototype was identified as ESP32-D0WD-V3 revision 3.1 with 4 MB
flash, a 40 MHz crystal and a CH340 adapter. Its exact carrier/module model
and external PSRAM are unknown. `esp32dev` is a generic build definition,
not a claim about the carrier manufacturer.

| Profile directory | PlatformIO environment | Chip target | Flash | Role |
| --- | --- | --- | --- | --- |
| `esp32-4mb` | `esp32-4mb` (default) | `esp32` | 4 MB | Current observed prototype |
| `esp32s3-16mb` | `esp32s3` | `esp32s3` | 16 MB | Original development target |

Both profiles use BOOT/GPIO0 for the optional physical factory reset and do
not require PSRAM. The ESP32 profile uses conservative DIO / 40 MHz flash
settings. Its application partition starts at `0x20000`, has size `0x3E0000`
and ends exactly at the 4 MB boundary. The S3 retains the original 4 MiB
application partition. Default NVS, PHY and application offsets/sizes are
unchanged. Both profiles use the former 24 KiB gap at `0x1A000` for a separate
`provision` NVS partition that survives application factory reset. Neither
profile implements OTA slots. A matching build is not hardware qualification.

Each profile owns:

- `platformio.ini`: board definition, flash parameters and explicit profile.
- `profile.cmake` and `sdkconfig.defaults`: target, flash and partition settings.
- `partitions.csv`: the layout for that hardware.
- `dependencies.lock`: generated by the component manager for that target.
- `include/netnode_board.hpp`: the small hardware interface used by shared code.
- Optional `components/`: board-specific component variants, only when a real
  incompatibility requires one. The build adds this directory when present.

Keep `main/` and the root `sdkconfig.defaults` common. Do not fork the transport,
portal, policy or upstream components merely to add another board. If a
component must diverge, retain that variant under the affected profile, document
its upstream version/license and the reason, and check that the selected build
actually resolves it. Keep API/security behavior shared; do not relax policy
or TLS to fit a board. No vendored component variants are needed currently.

Profiles are explicitly enumerated in the root CMake file. A target/profile
mismatch or a generated sdkconfig with the wrong flash/layout fails the build.
Use separate build directories and generated sdkconfigs per profile. Recreate
generated configuration when changing defaults; never edit a generated lock
by hand. PlatformIO retains the existing `esp32s3` environment name.

For a future C3 SuperMini, first read chip and flash, verify the BOOT pin and
USB interface, then add its own profile and perform a RISC-V cross-build and
the hardware checklist. No C3 settings are inferred from the ESP32 prototype.
