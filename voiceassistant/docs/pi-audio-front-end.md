# Pi/ReSpeaker 2-Mic audio frontend candidate

This is an unselected candidate. It changes neither the running Pi service nor
the server Meeting engine. The latter remains the owner of STT, turn steering,
waiting audio, confirmed barge-in, TTS and final speech-level regulation.

## Baseline measured on 2026-10-08

- Pi Zero 2 W, ReSpeaker 2-Mic HAT, WM8960 capture, MAX98357A I²S playout.
- Both analog capture mixer controls were `39/63`, reported as `+12 dB`.
  WM8960 ALC and noise gate were off.
- Application PCM used mono 16 kHz capture, mono 24 kHz playout and a fixed
  `40 ms` WebRTC stream-delay hint. AEC3, moderate NS and high-pass were on;
  client AGC was off.
- ALSA `plug` over `dsnoop`/`dmix` negotiated 125-ms periods and 375-ms
  buffers on both directions, despite 10-ms application frame requests.
- A short, low-level, RAM-only acoustic correlation probe measured about
  268 ms on cold first opening, then 87.7 and 89.1 ms on two warm openings.
  These include the diagnostic process's scheduling and are **not** a fixed
  production delay to copy into configuration.
- An isolated build of the Pi's WebRTC-AudioProcessing 1.3 accepted stereo
  capture with mono output. Its AEC3 delay estimate converged near 96 ms for
  synthetic audio delayed by 100 ms even with an external 40-ms hint. This
  proves internal delay tracking exists, not real-device AEC quality.

## Candidate graph

```text
WM8960 L/R PCM → bounded 10-ms stereo frames → WebRTC AEC3 + HPF + moderate NS
                 → mono output → bounded speech-gated prelevel → Meeting PCM
MAX98357A playout PCM after software volume/duck → WebRTC reverse reference
```

The new `captureChannels=2` path retains both microphones until the native APM
mono output. No custom beamformer has been added; compare stereo APM against
each channel and the previous mono path on actual near-/far-field utterances.
The low-latency ALSA configuration in `deploy/asound-lowlatency.example.conf`
is a **candidate**, not an accepted hardware setting. Verify negotiated period,
buffer, audible quality, underruns and CPU before selecting it. If a short
buffer causes TTS starvation, add a bounded jitter buffer at the node playout
boundary instead of silently restoring a 375-ms hardware buffer.

`prelevelEnabled` is off by default. The candidate controller observes the
post-AEC signal and APM voice/echo stats, learns a conservative quiet floor,
and applies at most +9/-9 dB with immediate peak protection. It neither
infers speech from loudness alone nor decays a useful far-field setting just
because the room is quiet. This is a *prelevel*, not a replacement for the
server's speech-focus controller. Before enabling it, compare server input
levels, estimated SNR, VAD, STT and false barge-in with and without it.
Expose raw pre-gain and applied gain as bounded metadata in a later reviewed
Meeting transport change; never present the post-gain level as untouched input.

`bargeDuckingEnabled` is also off by default. After 80 ms of sustained APM
voice evidence without strong residual echo it locally reduces playout to
20%, restoring after 200 ms without evidence. This only makes interruption
*sound* faster: it does not stop the shared agent turn or discard transcripts.
The Meeting engine still confirms interruption and clears output. Its value
depends on a verified low-latency PCM path; with the old 375-ms ALSA buffer,
the duck may be heard far too late.

## Delay and echo policy

Do not feed the AEC3 internal delay estimate back into `set_stream_delay_ms`
every frame. That would couple two control loops without proving the statistic
has the same meaning as the ALSA-system-delay hint. Use the external parameter
as a measured coarse hint, allow AEC3's own render-delay estimator to track
the changing acoustic path, and observe `delay_ms`, residual-echo likelihood
and echo return loss. Recheck after PCM restart, xrun and volume changes.
The current 40-ms hint is uncalibrated. A production value must be selected
with the final ALSA period/buffer configuration, not from the old probe.

## Separate output and server integration checks

- The MAX98357A click persists despite initial silence/fade. The existing
  code closes/reopens the ALSA stream on clear; with a lower-latency PCM path,
  compare persistent I²S silence versus reopening. An amplifier SD-pin mute
  would need a confirmed physical connection, not a software assumption.
- The Pi keeps capturing during TTS. Local ducking is only a candidate; the
  server Meeting engine remains responsible for final barge-in and retention
  of all utterances. Test first-word onset, echo-only speech false positives,
  user speech over TTS, and simultaneous waiting audio.
- Waiting music is not generated by the Pi. The voiceassistant Gateway adapter
  forwards it only when `waitingAudio` is configured. Verify the live config,
  transport push timing and AEC reference before changing audio algorithms.

## Acceptance before selection

1. Quiet room, 0.5/1/2 m speech, ordinary TV/loudspeaker echo and noise; compare
   the old mono path, each mic alone, stereo APM, then stereo plus prelevel.
2. Record only aggregate, non-content metrics by default: input and output
   RMS/peak, clipping, SNR estimate, AEC delay/echo stats, speech evidence,
   gain, PCM queue depth/underruns, CPU and end-to-end timing.
3. No regression in close speech, no persistent echo-triggered barge-in, no
   missed far-field first syllables after long quiet, and no double-AGC pumping
   with the unchanged server regulator.
4. Spoken TTS, waiting music and barge-in are audible without clicks or
   truncation. Keep a validated previous Pi release until the field test passes.
